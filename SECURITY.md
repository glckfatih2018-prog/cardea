# Security model and release review

Cardea is a self-hosted Stellar application that runs on **testnet by default**. The operator, PostgreSQL, host and institution signer configuration are trusted. Recipients and request bodies are untrusted. It never receives recipient private keys. The Stellar public network can be selected only by an explicit configuration that names the mainnet passphrase, carries the exact acknowledgement sentence, sets positive reserve and signer ceilings, uses a dedicated namespace, an HTTPS origin, the authenticated relay and the remote signer; each of these is enforced at startup and the persisted state is bound to one network. See [docs/MAINNET.md](docs/MAINNET.md). A compromised API or database can bypass application reserve limits. The isolated signer's daily count and fee ceilings and actual funded balances are the remaining financial bounds. A separate, unfunded mainnet pilot is deployed; no mainnet onboarding acceptance is claimed.

## Controls

- The server constructs and persists a fixed transaction body; it rejects modified payloads, extra operations, wrong networks, wrong/extra signatures and malformed signature hints before institution co-signing.
- Operator handlers use registered route metadata for authorization, including encoded request paths. Sessions are HttpOnly/SameSite=Strict, with exact-Origin and CSRF checks for mutations.
- Invitations are recipient-bound capabilities. Unsigned invitation retries are capped per invited recipient; public unsigned requests spend no per-recipient counter, so a third party naming an address cannot lock that address out. Only the recipient's own verified signature, followed by successful institution signing, consumes the per-recipient signed retry quota and the pool's signed daily admission counter.
- PostgreSQL serializes reservations across pools and channels. Signed envelopes and hashes are durable before submission; uncertain outcomes retain reservations and reconcile by hash. Worker transitions are guarded: only the current signed row with the same hash and attempt counter can be confirmed, expired or resubmitted, and a submission happens only when that transition committed. The worker lock is held until every reconciliation branch has settled.
- Sponsorship records own specific ledger entries (trustline, account or both). Reconciliation, graduation and handover act only on a record's own entries, so one wallet sponsored by the same institution account through two pools is accounted per pool. Absent entries observed at preparation release stale claims before a new reservation. Records are never repaired silently: an aggregate sponsor count mismatch auto-pauses the affected pools; maintenance that would touch an entry also claimed by another record of the same recipient and sponsor is refused before signing, including automatic graduation; a record with invalid units makes the monitor and maintenance throw, so the coherent reserve sample goes stale and new onboarding is blocked after the health interval rather than the pool being marked paused.
- Reserve and daily fee caps include pending obligations. Actual fees are booked to ledger inclusion day; transaction validity ends at the UTC budget boundary.
- Coherent ledger-bracketed reserve readings prevent mixed-ledger false pauses. Stale worker or monitor observations block new onboarding.
- A definitive failed graduation imposes a persistent 24-hour recipient cooldown, measured from the failed intent’s creation. Daily fees remain capped. Re-sending the same unknown envelope is not a new charge.
- Secrets are read from a private 0600 configuration file. The API binds to loopback; remote installations require TLS and a controlled reverse proxy.

## September 14, 2026 review

The implementation received source review by the implementing agent plus separate baseline and architecture reviewers, followed by targeted regression tests. This is **not an independent professional audit, penetration-test certificate, or assurance of zero vulnerabilities**.

Five findings in the pre-release implementation were repaired before publication:

| Finding                                           | Consequence before repair                                         | Repair and verification                                                                              |
| ------------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Encoded admin route authorization bypass          | Unauthenticated access to operator handlers when API is reachable | Registered-route guards; exact 401/403/200 GET and POST alias tests, including absolute-form targets |
| Unsigned preparation consumes shared daily quota  | One recipient can deny other recipients onboarding                | Recipient-bound invitation, per-recipient unsigned quota, signed-only shared admission counter       |
| Fees attributed to preparation day                | Midnight inclusion can misreport/exceed the next day's allowance  | Ledger inclusion date; expiry bounded by UTC rollover                                                |
| Inconsistent ledger snapshots pause healthy pools | Legitimate recipient activity can cause persistent false pause    | Retry observations crossing a ledger boundary, fail closed on stale coherent sample                  |
| Unbounded fresh graduation intents after failures | Recipient balance races can consume shared fees within daily cap  | Persistent recipient failure cooldown across intent IDs                                              |

The first four issues have controlled runtime reproductions; the fifth reproduces the missing cross-intent failure control, with the balance race established by source reasoning rather than an attack against public testnet. All repairs have regression coverage in `tests/audit-regressions.test.ts`. A malformed decorated-signature hint was additionally hardened and tested. The complete application suite passes 58 tests; `npm run security` runs a 16-test subset plus dependency audit, not 16 additional unique tests. The release dependency audit reported zero known advisories, including development dependencies, at the recorded time.

## Limits and operational risks

- The hardened Linux deployment runs a constrained signer under a separate OS identity; API/worker config contains no keys. The signer rebuilds fixed transaction templates and enforces independent persistent ceilings (100 distinct signatures and 1 test XLM in worst-case fees per UTC day). Host/root or signer compromise still permits signing abuse; this is not an HSM. API/database compromise may request policy-shaped sponsorships within those signer ceilings: pool/allowlist policy remains trusted application state.
- Horizon is the trusted source of testnet state; timeouts, stale ledgers and missing history block progress. There is no uptime guarantee.
- A signed transaction cannot be canceled by pausing the UI. Unknown outcomes must not be manually discarded or re-created.
- Authorized recipients can consume their own admission allowance; retry/fee caps bound resource abuse but cannot eliminate all denial of service.
- Recipients can change balances before a maintenance transaction lands. Failed ledger transactions can charge fees; the cooldown limits repeat failures rather than guaranteeing every graduation succeeds.
- Testnet resets can erase accounts and evidence. Preserve archived results and intentionally create a fresh installation after a reset.
- Database state is a serialized JSONB aggregate. It is scoped for one institution, not high-volume multi-tenant hosting. A namespace is not a security boundary.
- Tests use isolated PostgreSQL state and controlled ledger faults. Live testnet coverage and real wallet-extension acceptance are reported separately in [the evidence index](docs/evidence/README.md).
- Linux service templates, Docker setup and restore instructions are supplied; a remote production deployment and destructive backup-restore drill were not executed in this release.

Do not report secrets in public issues. Use the repository's private vulnerability reporting feature if available, or arrange a private channel with the repository owner before sharing exploit details or sensitive logs. No unverified contact address is prescribed here.

## Additional abuse hardening

- Hosted requests pass through a Vercel function that attests the platform client IP using HMAC. The API requires a fresh method/path-bound attestation when `relaySecret` is configured. Arbitrary forwarding headers are never trusted; per-client counters no longer collapse to the proxy IP.
- The signer Unix socket accepts only typed requests matching reconstructed onboarding/graduation/handover templates. Altered operations, role substitutions, invalid recipient signatures, expired requests and conflicting live channel sequences are rejected. Its journal is private to the signer user and persisted before signing. A timeout can conservatively consume a signing allowance even if no transaction lands; never delete the journal to bypass a ceiling.
- Horizon observations occur outside the state row lock; revision comparison retries stale observations before applying any reservation or signature. The signing IPC remains serialized with allocation, with a five-second timeout, to preserve crash and reservation safety.
- Vercel HTML receives CSP as well as Fastify-served HTML.
- Regression cases are in `tests/hardening.test.ts`; live deployment and verification results are reported with the change, not inferred from this document.

## September 28, 2026 review

Three defects found by a later independent source review were repaired with regression coverage in `tests/review-reproductions.test.ts`. As before, this is source review plus controlled runtime reproduction, not an independent professional audit.

| Finding                                                                                          | Consequence before repair                                                                                                                                                  | Repair                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public unsigned preparation spent the named recipient's per-pool retry counter                   | Three abandoned public requests naming a wallet blocked that wallet for the day, including its valid private invitation                                                    | Public requests spend no per-recipient counter; invitation abandonment keeps its own counter; a separate signed retry counter is consumed only after the recipient's verified signature and successful institution signing. Counters persisted by the previous release are ignored. |
| Sponsorship accounting compared wallet-wide sponsored entries against per-pool records           | One wallet sponsored through two pools of the same sponsor could not graduate in either pool, and a later user closure auto-paused both pools                              | Records own explicit entries; monitor, graduation, handover and confirmation operate on owned entries only; preparation releases entries observed absent before reserving                                                                                                           |
| The worker released its lock when one reconciliation branch rejected while another was in flight | A second worker could confirm a row that the orphaned branch later reset to UNKNOWN and resubmitted, double-booking fees, consumption and sponsorship and pausing the pool | All branches settle before the lock releases; every transition is guarded by current state, hash and attempt counter; terminal rows are never revived                                                                                                                               |

Residual behaviour that remains by design: an unsigned public request naming an address can exclude that address from another public onboarding until it expires (at most 180 seconds or the UTC rollover). A valid private invitation or operator maintenance supersedes such an unsigned hold. One trusted client identity may hold one unsigned public request at a time, but identity is not proof of a person and distributed clients can still occupy the public share. With two channels the public share is one slot. Signed in-flight requests cannot be superseded; they must settle. These controls bound, but do not eliminate, denial-of-service against public pools.
