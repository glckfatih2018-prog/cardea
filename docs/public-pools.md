# Invitation-free USDC trustlines (Stellar testnet)

Recipients enter `/app` → **Browse pools** → `/receive`, the public and private pool directory. Each row shows its name, description, access type, confirmed participants / participant limit, pending applications and availability. Filters and search help find a pool. Clicking opens `/receive/:id` with coverage, eligibility and participation details. Public pools lead to `/receive/:id/join` → connect Freighter on Stellar Testnet → review and sign. Private pools lead to the existing personal-invitation flow. This creates the testnet USDC trustline; it does not distribute USDC. If the account is not yet on-ledger, the same transaction creates it with zero XLM. Existing accounts without the trustline receive only the sponsored trustline. Accounts requiring additional signatures are rejected by this single-signature flow.

An authenticated operator explicitly selects **Pool access → Public** for an active pool. Existing private pools stay invitation-only. Both access types are discoverable, including paused/full pools: only the pool name, description, ID, access type, aggregate participant counts, participant limit and generic availability are exposed. Wallet addresses, allowlists, invitation seeds/links, reserves, fee budgets and internal pause reasons are not published. Operators should not put private information in names or descriptions. Invitations remain bound to allowlisted addresses. Public admission does not add wallets to the private allowlist. Switching a pool back to private blocks unsigned public requests at submission, even for an address that also happens to be on the allowlist. Already signed/submitted transactions cannot be recalled.

**Participant limits:** new pools default to 50; the operator can choose another positive integer up to 100,000, or leave the profile limit empty for no participant cap. Legacy pools keep their existing behavior with no invented limit. Counts mean distinct confirmed wallet addresses, not verified humans, and remain counted after graduation or closure. Pending onboardings reserve slots inside the same database transaction as channel/reserve allocation. The limit cannot be reduced below confirmed plus pending participation. Expired/failed requests release their slot when reconciled; signed requests with an unknown result continue reserving it. Participant limits are separate from XLM reserve and fee budgets. Profiles can be edited under **Pool details and participants** in the organization workspace. Directory data refreshes every 15 seconds and is rechecked by the server at preparation.

Reserve and daily fee caps, daily submission ceilings, rate limits, healthy-worker checks and the independent canonical signer apply to both paths. Recipient retry limits differ by path: an invitation holder's abandoned unsigned requests are capped per day, while public unsigned requests spend no per-recipient counter because anyone can name any address. A per-recipient signed retry limit is consumed on both paths only by the recipient's own verified signature. A pending unsigned public request naming an address does exclude that address from starting another onboarding until the worker expires it (180 seconds per request); repeated requests can renew that exclusion, bounded in rate by the channel share and IP limits rather than in total duration. Public pending requests may use at most half of the channel pool (minimum one); installations with a single channel cannot reserve a separate private channel. Wallet addresses do not establish unique human identity: public pools remain subject to Sybil budget exhaustion, so use a deliberately bounded testnet budget and pause when needed.

For a new account the sponsor reserves three base-reserve units; for an existing account's new trustline it reserves one. Fee accounting uses the exact operation count. Each sponsorship record owns the specific entries it created (trustline, account or both); a wallet that closes its trustline and later joins another pool of the same sponsor is accounted per pool, and graduation or handover in one pool releases or transfers only that pool's entries. Graduation and handover otherwise retain the same accounting and reconciliation mechanisms.

API: `GET /api/onboarding/directory` and `GET /api/onboarding/directory/:id` return directory metadata with no caching. The legacy `GET /api/onboarding/pools` retains the old active-public-only `{id,name}` response. `POST /api/onboarding/prepare` accepts either `{pool, recipient}` or `{invite, recipient}` (never both). The signed-XDR submit/status flow is unchanged. `POST /api/admin/pools/:id/access` accepts `{access: "private" | "public"}` and `POST /api/admin/pools/:id/profile` accepts `{name, description, participantLimit}`. Both require the authenticated operator session, exact origin and CSRF token.
