# Mainnet readiness

This document describes Cardea's Stellar public-network configuration, enforced controls, and remaining operator actions. As of 2026-09-30, a separate [mainnet pilot site](https://cardea.website) and isolated API, worker, and signer services are deployed. The four role accounts are funded on Horizon and their signing thresholds are set to 1; the read-only mainnet preflight passes for both service and signer. Two zero-XLM recipients were onboarded on mainnet through the production HTTPS API, one with a locally controlled signing key and one through Freighter. The public pilot pool is now visible in the [recipient directory](https://cardea.website/receive). The previous `cardea-mainnet-pilot.vercel.app` hostname permanently redirects to `cardea.website`, preserving the path. The existing [testnet site](https://cardea-site.vercel.app) remains separate.

## Network profile

A configuration names exactly one passphrase. That passphrase resolves to one immutable profile in `src/network.ts`; nothing else can be chosen or overridden:

| Profile | Passphrase                                       | Horizon                              | USDC issuer                                                | Explorer                                  | Faucet    |
| ------- | ------------------------------------------------ | ------------------------------------ | ---------------------------------------------------------- | ----------------------------------------- | --------- |
| testnet | `Test SDF Network ; September 2015`              | `https://horizon-testnet.stellar.org` | `GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5` | `https://stellar.expert/explorer/testnet` | Friendbot |
| mainnet | `Public Global Stellar Network ; September 2015` | `https://horizon.stellar.org`         | `GA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KZVN` | `https://stellar.expert/explorer/public`  | none      |

The passphrases and Horizon URLs were checked against [Stellar's network documentation](https://developers.stellar.org/docs/networks), and both USDC issuer IDs against [Stellar's asset documentation](https://developers.stellar.org/docs/build/agentic-payments/x402) on 2026-09-29. Any other passphrase, an empty value, or a padded value is rejected at startup. There is no runtime switch: the API, worker and signer each resolve the profile from their own configuration file and use it end to end (transaction building, signature verification, fee-bump wrapping, Horizon reads, trustline detection and the browser metadata route).

## What the code enforces on mainnet

- **Explicit opt-in.** `mainnet.acknowledge` must contain the exact sentence from `MAINNET_ACKNOWLEDGEMENT` in `src/config.ts`. A copied testnet file with only the passphrase changed does not start.
- **Explicit limits.** Positive `reserveCeiling` (total committed plus pending sponsored reserve across all pools, XLM), `signerLimits.count`, `signerLimits.fee`, and `signerLimits.maintenanceReserve` are mandatory. `publicDailyAdmissions` is also mandatory but may be `0` to disable public onboarding for a private pilot. No financial budget is guessed; templates retain placeholders for those decisions.
- **Dedicated namespace.** `namespace` must be explicit and must not be the default `cardea`. Persisted state is bound to the network on first initialization. A namespace bound to testnet refuses a mainnet configuration and vice versa. A populated row without a binding (written by earlier testnet-only releases) is adopted as testnet only. There is no migration from testnet data to mainnet; a mainnet namespace always starts empty.
- **Remote signer only.** The API and worker (`service` role) must set `signerSocket` and `keys: []`. In-process signing is refused for mainnet even if a configuration object bypasses validation. The signer process (`signer` role) must hold local keys and must not set `signerSocket`; an API file cannot be started as a signer and a signer file cannot be started as the API.
- **Signing network agreement.** Every signing request carries the passphrase. The signer refuses requests that omit it or name another network. The API verifies that the fee-bump returned by the signer carries a valid fee-payer signature over the hash for its own network, so a signer on the wrong network is rejected before anything is persisted. The signer journal is bound to one network and refuses rows from another. The mainnet signer also refuses a missing journal at startup and a missing or changed journal while running.
- **HTTPS origin and authenticated relay.** `origin` must be HTTPS and `relaySecret` must be set in the service configuration.
- **Installation reserve ceiling.** Enforced in the application for onboarding and handover, including pending intents across every pool, independently of editable per-pool caps.
- **Dedicated mainnet pool funding.** A configured sponsor account can be assigned to only one mainnet pool. A handover cannot move a sponsorship to an account assigned to another pool. The sponsor's private key is held by the isolated signer; the operator's personal funding wallet is never configured as a Cardea signer. Fund each dedicated account by a separate, amount-visible transfer from that wallet. The pool limit is an application policy, not an on-chain spending allowance; the amount deposited in the sponsor account is the physical exposure bound if the application policy is bypassed. The account's minimum balance and any outstanding sponsored reserves are not immediately spendable.
- **Independent signer ceilings.** Read from the signer's own configuration, persisted before each signature, and unaffected by API or database compromise.
- **Browser fail-closed.** The web app reads `GET /api/onboarding/network`, validates it against a fixed table, and disables wallet connection and signing when the metadata is missing or malformed. Before signing it re-reads the profile, checks Freighter's network, and verifies the complete unsigned transaction body against the expected sponsorship template. It never asks the wallet to switch networks. Explorer links follow the profile; the Friendbot link never appears on mainnet.
- **Testnet-only scripts refuse mainnet.** `setup:testnet`, `test:testnet` and `test:auto` stop before any network call if the configuration is not testnet.

## What the signer cannot prove

The signer rebuilds fixed templates and enforces daily count and fee ceilings. It does **not** read the ledger and cannot independently verify per-pool reserve budgets, allowlists or the sponsor's actual balance. An API or database compromise can bypass the application's `reserveCeiling` and pool limits. The independent signer ceilings and the actual funded balance remain the financial bounds, and neither makes the damage zero. Host or signer compromise exposes the keys; this is not an HSM and institution accounts are single-signature. The operator keeps control of their personal wallet, but XLM transferred to a pool's sponsor account is under the installation signer's control. There is no amount-scoped signer permission on a classic Stellar account: signer weights and thresholds authorize operations, not a fixed XLM allowance. Public client identity is derived from a trusted network edge, not from a verified person; it is an abuse throttle, not Sybil resistance.

## Fees and expiry

Cardea uses a fixed fee-bump fee of `baseFee` stroops per operation (default 1000, maximum 10000). Every prepared transaction expires after at most 180 seconds and strictly before the UTC day boundary. If the network's inclusion fee rises above the fixed fee during congestion, the transaction is simply not included: it expires, the channel sequence proves non-inclusion, the reservation is released, and no fee is charged. Cardea does **not** raise fees autonomously and does not bid against surge pricing. If expiries become frequent, the operator raises `baseFee` deliberately, within the schema limit, and restarts the services. The preflight reports the ledger base fee against the configured value.

## Freighter acceptance on testnet

On 2026-09-29, a real Freighter signature created a new account and a sponsored USDC trustline on Stellar testnet. Horizon returned 404 for the account before signing; after confirmation, the account and trustline existed, the account still held **0 XLM**, and the sponsor paid the fee. A separate real signature also sponsored a trustline on an existing funded account. This verifies the browser flow on testnet, not mainnet deployment or funding.

Freighter displayed an “insufficient funds for fee” warning for the zero-XLM account before allowing the user to review and sign. Its [published balance check](https://github.com/stellar/freighter/blob/bb0f75f3a484492f555545671355c45267681b43/extension/src/popup/helpers/balance.ts#L321-L327) requires available XLM to be strictly greater than the inner transaction fee, so zero available XLM with a zero inner fee can trigger that warning. The user dismissed it and the sponsor-paid fee-bump settled successfully. The onboarding page explains this case and tells users to cancel unless the wallet shows the correct network, expected sponsorship and USDC trustline operations, and a 0 XLM fee. This does not justify dismissing other wallet warnings.

## Mainnet acceptance and restore drill

On 2026-09-30, the production HTTPS API accepted a locally signed transaction for a previously nonexistent, zero-XLM recipient. [Horizon confirms the fee-bump transaction](https://horizon.stellar.org/transactions/aaaafcbbbdb85b8183646f839deac7f9afa47ad6ab5a0dd6a83fe31a4aaa6f7f): the recipient has a sponsored account and USDC trustline, holds 0 XLM, and the sponsor's entry count rose from 0 to 3. The Cardea intent reached `CONFIRMED`. See [public acceptance evidence](evidence/mainnet-pilot-20260930.json). A second [Freighter-signed mainnet transaction](https://horizon.stellar.org/transactions/1f3bd2ad1fc07776a8f75d817d6cd8880b7867196227c1a7ab0b8da25f4463df) completed the browser acceptance: the recipient is the sole signer, has 0 XLM, and has a sponsor-backed USDC trustline. See [Freighter evidence](evidence/mainnet-freighter-public-20260930.json). The pilot pool was then opened publicly with one admission per UTC day and the old private invite secret was rotated.

After the first transaction, an encrypted backup of the mainnet PostgreSQL database, service and signer configurations, and the nonempty signer journal was copied off-host. A temporary isolated database restored one state row, one pool, one confirmed intent and six audit rows; the restored signer configuration and one-entry journal loaded successfully. The temporary database and plaintext restore were removed. The live database was not used for the restore drill. The encryption private key and archive paths are held outside the repository. A root-owned systemd timer creates encrypted backups daily at 02:00 UTC; it briefly stops the three Cardea processes for a consistent snapshot, restarts them even on failure, and stores the encrypted archive on the host. After the Freighter acceptance and public opening, a fresh encrypted backup was copied off-host and its SHA-256 checksum verified. Future backups should also be exported off-host regularly: host-local copies alone do not cover host loss.

## Operational checklist (operator decisions and actions)

1. Generate one separate sponsor account per mainnet pool, plus channel and fee-payer keys offline, then install them only in the dedicated signer service's `0600` configuration. Never add the signer to a personal funding wallet. Never put role keys in the API or worker configuration, a browser, or the repository. The supplied Unix-socket deployment runs the signer and API as separate users **on the same host**: this is process isolation, not host isolation. Anyone who compromises the host or root account can reach the signer keys. Decide how many channels (throughput) and whether a second dedicated sponsor exists for handover.
2. Transfer only the intended XLM amount from a personal wallet to the dedicated sponsor account, and fund channel and fee-payer accounts separately. Verify the full destination address, network and amount in the wallet before signing. Decide the total budget and set `reserveCeiling`, `signerLimits`, per-pool `cap`, `feeCap`, `maxDailyAttempts` and participant limits accordingly. The current organization console uses preconfigured accounts; it does not create signer keys for arbitrary users or offer a personal-wallet allowance flow.
3. Start the private pilot with `publicDailyAdmissions: 0`; this hides public pool invitations and rejects public preparations even if a pool is accidentally marked public. Explicitly raise it only when opening public onboarding. Wallet addresses are not people; a public mainnet pool is a Sybil drain bounded only by your caps.
4. Keep the existing testnet installation running separately. Provision the three units in `deployment/mainnet/` as `cardea-mainnet-api`, `cardea-mainnet-worker`, and `cardea-mainnet-signer`, with separate `cardea-mainnet` and `cardea-mainnet-signer` users and a `cardea-mainnet-sign` socket group. Use root-owned `/opt/cardea-mainnet`, `0600` configurations under `/etc/cardea-mainnet/` and `/etc/cardea-mainnet-signer/`, and a dedicated PostgreSQL database and role (`cardea_mainnet`) on loopback. The mainnet API listens on 127.0.0.1:4318, the signer uses `/run/cardea-mainnet-signer/sign.sock` and `/var/lib/cardea-mainnet-signer/journal.json`, and the state uses a fresh namespace. Before its first signature, create the journal explicitly as `[]` with owner `cardea-mainnet-signer` and mode `0600`; after any signature, never recreate it without a reconciled restore. Never overwrite `/etc/cardea/config.json`, the `cardea-*` testnet units, or their database. Fill in `deployment/config.mainnet-service.example.json` and `deployment/config.mainnet-signer.example.json`; every `<...>` placeholder must be replaced. The templates deliberately fail validation until those decisions are made.
5. Use a separate HTTPS pilot site and relay pointing only to the mainnet API on port 4318. Set the service configuration's `origin` to the exact browser origin, currently `https://cardea.website`, so browser POST requests pass the origin check; other origins remain rejected. Set the site's `CARDEA_API_ORIGIN` to the backend HTTPS gateway used by the relay, and set its `CARDEA_RELAY_SECRET` to the same secret as the mainnet service. The relay's backend origin and the browser origin serve different purposes and need not be equal. Do not repoint the live testnet site during pilot acceptance.
6. Start the signer, API and worker with empty mainnet state and no funded public pool. Run the read-only preflight for both roles and keep the JSON output:

   ```sh
   CARDEA_CONFIG=/etc/cardea-mainnet/config.json npm run preflight:mainnet
   CARDEA_CONFIG=/etc/cardea-mainnet-signer/config.json npm run preflight:mainnet -- signer
   ```

   Preflight validates configuration, live worker and monitor state, state binding and reserve counters, the signer socket, Horizon identity and freshness, role account signer thresholds and balances, and aggregate sponsor liquidity for the configured installation reserve ceiling. It rejects role accounts with another active signer or account responses older than the final observed ledger; retry if Horizon advances during the check. Per-pool sponsor capacity remains enforced during pool activation and transaction preparation. It never signs or submits. `--offline` explicitly returns `ready: false`; it is useful only for partial diagnostics. Passing preflight is necessary, not sufficient.

7. Confirm `/api/health` reports `"network":"mainnet"` and `/api/onboarding/network` reports the mainnet profile through the relay.
8. Create one paused pool with a deliberately small cap, activate it, and complete one real Freighter onboarding with a wallet you control. Record the transaction hash, then raise limits only as far as your budget decision allows.
9. Back up the signer configuration, signer journal and PostgreSQL together, encrypted, and perform the restore drill in an isolated environment before opening the pool to others.
10. Arrange an independent security review before treating this as production-ready. Local regression tests and self-review are not an external audit.

## Keeping the testnet workflow

Nothing changes for local development: `npm run setup:testnet` still writes an in-process testnet configuration with default signer ceilings, and the test suite still runs against a testnet-bound fixture. The optional `reserveCeiling` and `signerLimits` fields may also be used on testnet.
